# Architecture review · 3-Nov-2026

Read-only inventory of the whole tree before reordering it. Carlos asked for it on 3-Nov
("tenemos midi, wav, vcsl, ace step, sonido, mousepad... creo que estoy haciendo un lío").
Nothing in this document changes code; it measures what is there and proposes where to cut.

Method: four reviewers in clean context (browser layer, server layer, domain + engines,
documentation), each with the code and no conclusions handed to them; their reports were
cross-checked against each other and the gravest claims were re-verified by hand on
commit `b93f85c`. Baseline that morning: `tsc --noEmit` 0 errors, `npm run test:unit`
245 tests green, `smoke.py` OK.

Sister documents: `docs/REVISION-2026-10-27.md` (the previous review), `ESTADO.md`
(handover), `docs/ARCHITECTURE.md` (which this review shows to be stale in its numbers).

---

## 1. The diagnosis in one paragraph

The feature count is not the problem. Almost everything that brings material into a song
already converges on one door (`importarPistas` in `web/src/agent/acciones.ts`), the
project model and its transactional ops are sound, and the pure domain in `src/core` is
pure (0 DOM/fetch/node references measured) and tested. What has gone wrong is that nine
layers of work (humseed, Python engine, openDAW, VCSL, GM, GPU models, pad, prices,
trajectories, authorship) were added without anyone re-reading the whole. The result is
measurable: three files hold 42 % of the TypeScript, the same WAV import flow exists four
times in the browser and six WAV readers exist in Python, the 31 agent tools are declared,
coerced and dispatched by hand in one 598-line `switch`, 38 server routes are served
through five different process wrappers, and the state of the project is written in five
pending lists, four decision logs and three roadmaps that already contradict each other.
The fix is not fewer features; it is one owner per concern and one copy per rule.

## 8. Proposed spines (hypothesis for Carlos to confirm)

Everything above fits five axes. A capability that does not sit on one of them is a
candidate to park.

1. **The song**: `src/core` types + ops + validation + the on-disk format (move
   `proyecto-archivo.ts` here). Only `applyOps` mutates it. One track resolver, one
   note-name table, one bar convention.
2. **One door for material**: `importarPistas` for everything that becomes a track or a
   clip (file, agent, Strudel, bundle, pad recording, GPU take, transcription, proposal).
   Sources plug into it; they never write ops of their own. This is where ACE-Step
   `extract` and `lego` would enter without adding a path.
3. **Sources of material**: engine voices (GM, VCSL), the Python engine, the GPU models,
   the pad, the catalog. Each one is a module that returns files or notes, nothing else.
4. **Listening and measuring**: `escuchar_mezcla`, `exportar`, `verificar_audio`,
   `medir_referencia` and the openDAW offline render, moved out of `main.ts` into a
   module next to `opendaw-engine.ts`.
5. **The agent and its plumbing**: loop, one tool table (`Record<name, {schema, validate,
   run}>` with zod, replacing the `switch`), providers, prices, trajectories. The prompt
   stays frozen (house rule 1).

On the server the equivalent is: one spawn helper, one route wrapper, one path resolver,
`contexto.ts` reduced to the real shared surface (`responderJson`, body readers, paths,
`anotar`, `correr`, `slugProyecto`), single-consumer helpers moved next to their route.
